**Claim.** `v4.33.0-rc1` accepts two distinct axiom-free proofs of `False`. Both were
fixed on `master` and shipped in the `v4.32.2` patch release, but neither was
cherry-picked into the 4.33 branch, which was cut before both fixes landed.
Unless they are forward-ported, stable `v4.33.0` will ship with both holes.

All results below were produced with an explicitly pinned toolchain
(`elan run leanprover/lean4:<v> lean --trust=0 <file>`) and verified in-band
(`lean --version` reported `4.33.0-rc1, commit 62eed1db4d67327ec8120be05f1a1b0847d74561`).

## Bug 1 — issue #14576, nested-inductive parametric arguments escape checking

Fixed by PR #14577 in `src/kernel/inductive.cpp`.

In `elim_nested_inductive_fn`, a nested occurrence `I Ds is` is replaced by an
auxiliary type `Iaux As is`. The aux type is built by `instantiate_pi_params`,
substituting `I`'s parameters with `Ds` **without type-checking `Ds`**; `Ds` is
consumed and never appears in the aux declaration, so it escapes all kernel
checking. A wrong-structure projection (`mkProj C 0 w` with `w : W`) is placed
into that position, disguised by a deliberate `Expr.hash` + `approxDepth`
collision so the defeq machinery does not separate the two terms.

Note the pre-existing structure-name check in `infer_proj` was never the defect —
it exists in `v4.32.0` and simply was not reached on the escaping argument. A
finer point: a separate aux-inductive universe-level check catches escaping
values whose ill-typedness is *statically* visible, so only values whose
ill-typedness requires reduction to detect (wrong-structure projections on a
still-abstract scrutinee) get through.

Results (repro = PR #14577's `tests/elab/issue_14576.lean`):

| Toolchain | Result |
| --- | --- |
| v4.27.0-rc1 | accepts — `'boom' does not depend on any axioms` |
| v4.31.0 | accepts |
| v4.32.0 | accepts |
| v4.32.1 | accepts |
| v4.32.2 | **rejects** — `(kernel) invalid projection w.1` |
| v4.33.0-rc1 | **accepts** — exit 0, axiom-free |

Source-level confirmation, `src/kernel/inductive.cpp`: the fix block is present on
`master` and `v4.32.2` (1260 lines) and **absent** on `v4.33.0-rc1` (1249 lines).

Both ingredients are essential. Replacing the collision padding (78670 /
24083, both hashing to 3438362649 at depth 2) with non-colliding constants makes
`v4.32.0` correctly reject with `(kernel) application type mismatch`. The fix is
complete against depth: 2- and 3-level nestings are accepted on `v4.32.0` and
rejected on `v4.32.2`. Malformed projections in *index* position were never
affected, and are rejected on both.

## Bug 2 — issue #14484, `opaqueDecl` does not reject free variables

Fixed by PR #14498 (`fix: kernel to check opaque values for fvars`).

`environment::add_opaque` omitted the `check_no_metavar_no_fvar` closure
validation applied to other declaration kinds, so an opaque's value may reference
a free variable that primes the typechecker cache.

| Toolchain | Result |
| --- | --- |
| v4.32.0 | accepts — `'assumptionFreeFalse' does not depend on any axioms` |
| v4.32.2 | **rejects** — `(kernel) declaration has free variables` |
| v4.33.0-rc1 | **accepts** — exit 0, axiom-free |

## Scope

Both require `import Lean` and a metaprogram reaching the kernel through the
ordinary *checked* `addDecl` path. Neither uses `sorry`, `native_decide`,
`unsafe`, `addDeclWithoutChecking`, `debug.skipKernelTC`, FFI, or modified
`.olean` files; both run under `--trust=0`; `#print axioms` reports no axioms for
both. As the #14498 discussion notes, practical risk is bounded because a
metaprogram must already be executing in-process, and the export format
plus external checkers are unaffected. The concern here is narrower and concrete:
a shipped stable release regressing two already-fixed kernel soundness holes.

## Reproduction notes

Bare `lean <file>` resolves the toolchain from the *current directory*. In a tree
with no `lean-toolchain`, that is the elan default, which rejects both repros.
Always pin explicitly:

    elan run leanprover/lean4:v4.33.0-rc1 lean --trust=0 Bug.lean

Judge acceptance by exit code and `#print axioms`, not by grepping for `error`:
one probe in this investigation aborted with a stack overflow (exit 127) while
printing no `error` line. Note also that `Lean.addDecl` is asynchronous in
4.32.x, so a `try`/`catch` around it silently reports rejections as acceptances;
use `set_option Elab.async false`, or the synchronous
`(← getEnv).toKernelEnv.addDecl {}` and `Lean.Kernel.isDefEq`.
